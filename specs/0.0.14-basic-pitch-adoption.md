# MCC 0.0.14 — Basic Pitch Adoption (audio → notes front-end)

Multi-version, phased adoption of Spotify's **Basic Pitch** (open-source, Apache-2.0, on-device Core ML model) as the *audio → notes* front-end for MusicCraftCore, replacing the hand-rolled YIN pitch detector and the RMS-energy onset detector. Basic Pitch hands MCC polyphonic note events plus a frame-level pitch contour; MCC keeps every downstream stage that turns notes into meaning (chord naming, key inference, tempo, music theory, guitar voicings, the melody→supporting-chords gold feature).

This spec covers the whole adoption. Code lands across three reversible, measured versions; **0.0.14 ships Phase 1 only** (vendor the model + a `BasicPitchTranscriber` + tests, with no wiring into `AudioExtractor`). 3-component SemVer tags only.

**Tier / classification.** Phase 1 is additive — one new public type plus a bundled model resource, no change to `AudioExtractor` or its `Result`. That alone is Tier 2 / yellow. But it integrates third-party code and a third-party model, which triggers the portfolio **third-party-integration security-review gate**: a security analysis must be filed and linked from the implementing commit *before* the transcriber is integrated. Phase 1 does not tag until that analysis exists. Tag `0.0.14` after review + tests pass.

---

## Problem statement

The current `AudioExtractor` pitch path is the app's weakest link, and it is hand-rolled DSP:

- `DSP/PitchDetector.swift` — YIN (vDSP) with a confidence-weighted median smoother. **Monophonic only.** It runs on the full voice+instrument mix, so a loud guitar pulls the inferred pitch off the sung melody and the downstream key inference goes wrong.
- `DSP/OnsetDetector.swift` — RMS-energy onsets used for note/chord segmentation. RMS rises on every intra-strum articulation, not on beat/note boundaries.
- Chord detection on real guitar measures **31–40% root accuracy** (GADA fingerstyle / TaylorNylon classical subsets), which is why Sanctuary's chord display is currently held off (slice 10 reverted).
- The note output is **nondeterministic run-to-run** (Swift hash-seed ordering); the eval has to pin `SWIFT_DETERMINISTIC_HASHING=1` to get stable numbers.

These are the most bug-prone things MCC owns: stuck pitches, octave jumps, median-filter tuning, onset thresholds, and the hash-order note instability. A pretrained neural transcriber addresses the cause rather than the symptoms: it is polyphonic (the monophonic limit goes away), its inference is deterministic given fixed input (the hash-order bug goes away outright), and it is very likely a real accuracy step up exactly where the app is weakest — bad note/pitch input is what currently breaks the harmony pipeline.

## What we adopt, what we keep, what we consolidate

**Adopt — the audio → notes stage only.** Basic Pitch provides per-frame pitch contour, note onsets, note events, pitch bends, velocity, and polyphony. That replaces the YIN path and the RMS onset path.

**Keep — everything downstream.** Chord naming, key inference (`MelodyKeyInference`, Krumhansl–Kessler), `ProgressionAnalyzer`, diatonic generation, enharmonic spelling, tempo, the Guitar Voicings subsystem, and the melody→supporting-chords gold feature all stay. Basic Pitch hands back *notes*, never a chord / key / tempo / mood — MCC turns notes into meaning. The public `AudioExtractor.Result` shape (`chordSegments`, `key`, `contour`, `detectedNotes`, `duration`) is **preserved unchanged** through Phases 1–2 so Sanctuary needs no change.

**Consolidate — chord detection too, if it earns it.** Decision (Chris, 2026-05-31): if Basic Pitch can reliably solve chord detection, use it for everything and reduce the stack. Chord accuracy has two existing candidate routes — the chroma + template pipeline (shipped, ~31–40%) and a trained CreateML `MLSoundClassifier` (a paused effort; a trained model already sits in `mossgroves-music-craft-core-training/` r1–r4b, projected 85–92% on solo nylon). Basic Pitch adds a third: re-derive chords from its real polyphonic notes (with bass), which also unlocks inversions / slash chords. **This spec does not assume Basic Pitch wins chords** — dense strummed chords on nylon are Basic Pitch's known soft spot. Phase 2 benches all three on the same labeled fixtures and on Chris's own nylon recordings. If the Basic Pitch route matches or beats the trained model, Phase 3 consolidates on it and retires both the chroma+template path and the trained-model route (maximum stack reduction). If it falls short specifically on nylon chords, the trained model is the fallback. The trained CreateML model is **kept as the Phase 2 benchmark**, not deleted.

## The three phases (reversible, measured)

**Phase 1 — vendor + wrap (0.0.14; additive, safe to delete).** Add Spotify's official Core ML serialization to `Sources/MusicCraftCore/Resources/`. Verify the exact artifact against the `spotify/basic-pitch` repo (model card / MANIFEST) and confirm it compiles to `.mlmodelc` through the xcodegen/Xcode build — `swift build` on the CLI may not run `coremlc`, so if it doesn't, commit the precompiled `.mlmodelc` as the resource. Add a `BasicPitchTranscriber` that takes a mono buffer (resampled to the model's input rate), runs inference, and returns note events plus the frame-level pitch contour. Unit-test against `AudioAnalysis/Fixtures`, including a determinism test (same input → byte-identical output). **No wiring into `AudioExtractor`.** Fully reversible: delete the type + the resource.

**Phase 2 — dual path behind a flag + bench (0.0.15, provisional).** Add an `AudioExtractor.Configuration` toggle selecting the note source (Basic Pitch vs. the YIN path as fallback), preserving the public `Result` shape. Two new design points live here: (a) a **monophonic reduction** from Basic Pitch's polyphonic notes to feed the existing `DetectedNote` / `ContourNote` / `MelodyKeyInference` melody path; (b) **chord-from-notes** naming from the polyphonic set. Run both note paths — and all three chord routes — through `cantus-eval` on labeled fixtures and compare note/melody accuracy and chord accuracy with numbers, not impressions. This is the go/no-go signal for the chord consolidation and for the v1.0-gated UI features.

**Phase 3 — flip + delete (0.1.0; the stability milestone).** Once the eval and Chris's nylon + vocal recordings inside Songcatcher confirm it holds, make Basic Pitch the default, deprecate the YIN path, then remove `PitchDetector`, the RMS `OnsetDetector`, and the `detectNotes` mode logic — and, if the chord head-to-head went its way, the chroma+template chord pipeline — in a tracked cleanup (`TASKS.md` MUST REMOVE; no release ships with an open MUST REMOVE). **Keep `SpectralFluxOnsetDetector`** (it serves the tempo path). 0.1.0 is the milestone earned *after* the new engine proves out and the old one is gone — not the start of the swap.

## Proposed Phase 1 API

New public types in a new `Transcription` area. Exact field names firm up against the model's actual output during implementation:

```swift
public struct BasicPitchTranscriber {
    /// Loads the bundled Basic Pitch Core ML model.
    public init(configuration: Configuration = .default) throws

    /// Transcribe a mono PCM buffer. The buffer is resampled to the model's
    /// input rate internally; callers pass audio at any sample rate.
    public func transcribe(_ samples: [Float], sampleRate: Double) throws -> Transcription

    public struct Configuration: Equatable, Hashable, Sendable {
        public let onsetThreshold: Double        // note-onset activation gate
        public let frameThreshold: Double        // per-frame pitch activation gate
        public let minNoteDurationMs: Double     // drop spurious ultra-short notes
        public static let `default`: Configuration
    }

    public struct Transcription: Equatable, Sendable {
        public let notes: [TranscribedNote]      // polyphonic note events
        public let contour: [PitchFrame]         // frame-level pitch posterior
        public let duration: TimeInterval
    }
}

public struct TranscribedNote: Equatable, Hashable, Sendable {
    public let pitchMIDI: Int
    public let onsetTime: TimeInterval
    public let duration: TimeInterval
    public let velocity: Double                  // 0…1 (model amplitude)
    public let pitchBend: [Double]?              // per-frame semitone deviation, if present
}

public struct PitchFrame: Equatable, Hashable, Sendable {
    public let time: TimeInterval
    public let frequencyHz: Double
    public let confidence: Double                // 0…1
}
```

These are purely additive. Mapping `[TranscribedNote]` down to the existing monophonic `DetectedNote` / `ContourNote` (for `MelodyKeyInference`) and the chord-from-notes naming are **Phase 2** concerns — Phase 1 only exposes the transcriber.

## Model artifact, dependencies, supply chain

- Bundle Spotify's official Core ML serialization as a resource in `Sources/MusicCraftCore/Resources/`, exactly like the bundled `guitar_voicings.json`. **Zero new third-party dependencies**: Core ML is an Apple system framework, so `Package.swift` stays `dependencies: []` and the model ships as a `.process("Resources")` (or precompiled `.mlmodelc`) resource.
- **Pin + checksum** the bundled artifact; record its SHA-256 and source URL/commit in a provenance note and in `NOTICE`.
- **Apache-2.0**: include the upstream LICENSE text and a `NOTICE` entry attributing Basic Pitch and noting the artifact is used as-is (or noting any change). No code conversion needed — Spotify ships the Core ML serialization.
- A small resampler (vDSP) is the one new bit of DSP this adds (input-rate → model-rate). Bounded, pure, unit-tested.

## Security review (required, gating)

Per the portfolio rule on integrating third-party code/algorithms, file a security analysis **before** integrating the transcriber and link it from the implementing commit (e.g. `docs/security/basic-pitch-2026-05-31.md`). It must cover: artifact provenance and supply-chain risk of the model + any vendored preprocessing; what the binary resource contains; **on-device confirmation via packet capture** that nothing leaves the device at inference (the privacy promise); input/bounds safety in the resampler and buffer handling; exception design on model-load and inference failure; and any known advisories. Classify SAFE TO ADOPT (with Swift adaptation notes) or UNSAFE (with reasons). Given Songcatcher's privacy-first, on-device posture, the packet-capture step is load-bearing, not pro-forma.

## Validation gate (before deleting anything)

Two gates, both required, before Phase 3 deletes the YIN path:

1. **cantus-eval on labeled fixtures** — old-vs-new note/melody accuracy, and chord accuracy head-to-head across the three routes (chroma+template, trained CreateML model, Basic-Pitch-notes→chords). Pin `SWIFT_DETERMINISTIC_HASHING=1` for the legacy path; the Basic Pitch path is deterministic by construction.
2. **Chris's own recordings inside Songcatcher** — nylon (Taylor 812ce-n / Lowden SJ-32) fingerpicking and dense strummed chords, plus vocal melody. Special attention to Basic Pitch's known soft spots: nylon timbre and dense strummed chords.

Numbers, not impressions. The chord-consolidation decision is made on these numbers.

## Out of scope here

- **Tempo.** Basic Pitch does not estimate tempo; the tempo perceptual-prior fix (an IOI-histogram metrical-level prior, à la Ellis 2007) is a separate track. `SpectralFluxOnsetDetector` and the `TempoEstimator` family are kept untouched.
- **App UI.** The capability this unlocks (polyphonic notes, frame contour, pitch bends, velocity) is announced to Sanctuary separately. The two app-facing UI ideas it enables — a vocal pitch-contour view and a fretboard/tab view — **need mockups before any UI slice** and are tracked in Sanctuary `BACKLOG.md`, not here.

## Interactions with in-flight MCC work

- **`AudioExtractor.Configuration` Hashable removal.** A paused branch added an optional `classifierProvider: ChordClassifierProvider?` to wire the trained CreateML model, which would have dropped `Hashable` from `Configuration` (protocols can't be `Hashable`). If the chord consolidation lands on Basic Pitch, that protocol-injection approach likely becomes unnecessary and the `Hashable` break is avoided. Flagged, not decided here — revisit at Phase 2 once the head-to-head result is known.
- **The trained CreateML model** (`mossgroves-music-craft-core-training/` r1–r4b) is **retained as the Phase 2 chord benchmark**, not deleted, regardless of outcome.

## Migration notes for consumers

- **Sanctuary** — no change through Phases 1–2; `Result` is shape-identical. At the Phase 3 flip, behavior improves (cleaner notes/key/contour, possibly chords) with **no public signature change**. If the new note path shifts `MelodyKeyInference` score distributions, recheck `HarmonyKeyGate.minScore` (currently 0.5, provisional) — but validate against the audio path before changing a shipped gate (per the 2026-05-31 recommendation).
- **Other consumers** (Guitar Atlas) — none through Phase 2; same Phase-3 note.
